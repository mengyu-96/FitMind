# 项目总体设计

版本：v1.3｜日期：2026-09-25｜状态：沿用已确认C01—C10基线，按用户要求深化智能体自由度与主动交流

> v1.3实施范围：M0仅微信小程序，模块化单体保留；肌肉图、实时训练工作台、离线提醒与管理Web在后续阶段实现。 具体分期与自主授权以[29](29-微信小程序首版收束与智能体授权.md)为准。

## 1. 产品目标与边界

FitMind 是以对话为入口的健身陪伴小程序。用户通过“了解自己 → 制定计划 → 执行训练 → 看见变化 → 调整计划”形成闭环；资料卡承载长期信息，知识引用增强建议可核查性，肌肉图解释训练覆盖和估算疲劳。

建议首批服务有基础健身条件的成年新手及进阶者。首版不承诺诊断、康复治疗、真实肌肉测量、保证增肌减脂或突破成绩。首版成功定义为用户能持续记录并理解训练建议，而非聊天次数增长。

## 2. 系统结构

```mermaid
flowchart TD
  U[微信小程序 / uni-app] --> A[FastAPI 鉴权与API]
  W[内部审核导入 / 受限接口] --> A
  A --> B[领域服务：柔性事实、变更、授权、业务投影]
  A --> G[Agent主规划器与能力网关]
  G --> I[关注议程：观察、反馈、提问、吸收回答]
  I --> B
  G --> B
  G --> R[RAG与个人记忆检索]
  G --> L[可替换模型适配器]
  B --> P[(PostgreSQL + pgvector)]
  R --> P
  B --> O[事务Outbox]
  O --> Q[Redis Streams]
  Q --> J[Worker：索引、导出、删除；肌肉与提醒后置]
  J --> B
  A --> S[对象存储：授权媒体]
```

建议模块化单体，API与Worker独立进程。避免在首版引入微服务运维成本。PostgreSQL为事实来源，Redis仅缓存与任务传输；客户端和模型均不能直接写数据库。

## 3. 技术基线

| 层 | 建议选型 | 取舍 |
|---|---|---|
| 小程序 | uni-app、Vue3、TypeScript、Pinia、SCSS | 延续原文；真机优先验证 |
| 可视化 | 受控SVG资产+图片/点击层；Canvas备用 | 不依赖浏览器SVG DOM能力 |
| 后端 | Python 3.12独立Conda环境、FastAPI、Pydantic、SQLAlchemy、Alembic | 与base隔离，统一输入校验与迁移 |
| 数据 | PostgreSQL16、pgvector | JSONB灵活字段和关系约束并存 |
| 异步 | Redis Streams、事务Outbox、独立Worker | 可补发、可观测；重复消费幂等 |
| Agent | LangGraph状态编排+自有能力网关+供应商适配器 | 主教练自由编排可组合能力模板；领域事务保持独立，见19/25/28 |
| 检索 | 中文关键词+向量、可选重排 | 模型与维度配置版本化 |
| 部署 | Docker Compose、托管数据库可选、CI流水线 | 具体云厂商待确认；单机有故障窗口 |

供应商、精确依赖版本、区域和价格在获准开工后的技术验证里冻结，不能把“可替换”理解为未经评测即可热切换。

## 4. 关键数据流

1. 对话：鉴权 → 保存消息及运行ID → 安全分流 → 获取个人上下文/知识 → 提议工具动作 → 服务端校验执行 → 保存结果 → 返回回复、卡片版本和引用。
2. 记录训练：保存用户明确描述的柔性源对象 → 按消费者需要建立可用训练投影 → 源修订、即时投影和outbox同事务提交 → 返回已保存及计算资格 → Worker更新派生结果。无组数也可保存，计算失败不丢记录。
3. 修改历史：新增修订版本 → 废弃旧投影输入 → 从有效事实重算 → 原有报告保留版本说明。
4. 主动交流：事件/用户消息触发 → 读取关注议程与有效来源 → 判断直接帮助、反馈或提问 → 吸收自由回答更新理解；离线跟进另查授权/静默/频控与最新答案版本，再生成站内消息和尝试订阅通知。

## 6. 演进触发

Agent运行采用可持久化状态图、带版本的检查点、业务工具回执、确认票据、用户级执行租约和硬预算。检查点不替代数据库事务；恢复依赖工具幂等回执。完整设计及新验收案例见[19-Agent架构优化设计](19-Agent架构优化设计.md)。

只有出现经监控证实的瓶颈才引入独立搜索/向量集群、复杂编排或服务拆分。多场馆租户、支付结算和教练权限需要单独设计；当前为其保留逻辑边界，不宣称已支持。

## 7. v1.2设计约束

可信包络固定，个人业务语义开放；fitness_objects为事实源，传统业务表为投影。智能体可主动探索目标、创建个人类型/属性、选择工具与问题、组合视图，并在明确意图或有限委托内行动。依据不足只影响相关动作，不阻塞全部服务。通过稳定operation_id、版本、服务端授权与task预算保证执行可靠，不能把这些系统约束变成用户必填表。见25—28，应用开发仍等待文档阶段确认。

## 8. M0架构落实

首版一个主规划循环+共享工具网关+统一领域变更服务。开放对象及来源、版本、操作回执是基础；议程、交互偏好与委托可复用对象存储和索引，不先建设各自独立平台。apply_changes内部完成校验与授权匹配，已授权直接提交；Agent自由交织读取、检索、记录、修改、汇总及展示。

02的肌肉性能项、SVG资产及后台提醒数据流属于后置专项；M0仍验收核心API、对话响应、写入可靠性及灾备。uni-app只交付mp-weixin，后端承担Agent运行，不将跨端发布作为首版收益承诺。

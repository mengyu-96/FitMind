# 智能体自由度与柔性业务内核

版本：v1.3｜日期：2026-09-25｜依据：用户明确要求深化覆盖并最大程度保留智能体自由度｜状态：设计修订，未实现

> v1.3实施范围：自由语义与自主执行是M0核心；完整个人Schema平台、条件排程、后台自治及复杂可视化后置，授权与工具直执行以29为首版细化。 具体分期与自主授权以[29](29-微信小程序首版收束与智能体授权.md)为准。

## 1. 核心决定

**系统固定可信执行的边界，智能体决定信息结构、任务路径和呈现方式。** 数据库的标准训练表是用于计算和查询的投影，不是用户必须填完的表单，也不是智能体唯一可以保存的信息结构。

v1.2将“全部字段完整才允许继续”改为“先保存明确陈述，按动作判断是否有足够依据”。“用户报告练了腿”是一条真实的用户自述；它并不证明做了4组深蹲。系统可以保留前者，同时不生成后者。存储成功、可规范化、可计算、可以建议是四个独立结论。

用户可以通过一句话开始，也可以一次提供一大段信息；智能体无需先完成固定问卷。用户主动选择精确录入时仍提供编辑组件，但组件是辅助能力，不是默认业务入口。

## 2. 自由度分层（AU-01）

| 层次 | 智能体可以自主决定 | 系统必须保障 |
|---|---|---|
| 对话 | 先回答还是追问、语气、问题顺序、必要时跳过提问 | 不编造用户回答，不重复询问已拒绝的非必要问题 |
| 个人信息 | 自定义属性、主题、目标、状态、记录粒度、对象关系 | 所有权、来源、用途授权、版本、删除可追踪 |
| 任务组织 | 分解/合并子任务、选择工具和子图、跨轮继续 | 权限、预算、幂等、事务与可取消性 |
| 计划内容 | 单次/短期/轮换计划、动作组合、表达详略、条件分支 | 当前动作适用性、已知限制、不自动伪造采纳 |
| 展示 | 选择文字/卡片/列表/图表、字段标签与顺序、局部布局 | 受控组件、数据引用、用户隐藏/置顶优先、无任意代码执行 |
| 主动性 | 提议有依据的关注事项、回访时机、调整方案 | 用户授权范围、静默与频控，不后台无限自唤醒 |
| 自定义语义 | 创建个人类型、声明单位、提出概念映射和指标 | 不把个人标签自动发布为全局知识或医学公式 |

必须固定的是资源ID、用户归属、审计和版本等协议元数据，不是“你只能有身高、体重、目标这几个属性”。网络和数据库接口需要schema，但schema应首先约束信封与执行效果，业务payload允许扩展。

## 3. 权威数据路径（AU-02）

```mermaid
flowchart LR
  U[自然语言 / 可选精确录入] --> O[个人业务对象与来源声明]
  O --> V[用途与证据检查]
  V --> P[版本化领域适配器]
  P --> T[训练/画像/计划/指标投影]
  O --> C[动态视图与安全组件]
  T --> C
  C --> U
```

核心表fitness_objects保存用户个人记录、偏好、目标、计划模块、关注事项等灵活对象；object_revisions记录版本，claim_evidence记录属性/声明对应证据，object_relations记录关系，projection_bindings记录映射。`kind`是个人可扩展语义标签，不是只有几个枚举才能写入的业务限制。

已有profiles/training_sessions/training_sets/plans等成为领域投影与执行索引。对规范化录入也通过同一领域服务生成来源对象，再同步提交可用投影，避免“对话写一份、表单写另一份”互相覆盖。授权、登录、账本、发布审核等系统对象继续采用固定模型，不开放成任意payload。

无需引入完整事件溯源框架：采用当前对象+不可变修订+关系+outbox即可；读取当前状态不需要回放全部历史。不能以“灵活对象”名义取消关系完整性和必要数据库约束。

## 4. 最小对象信封（AU-03）

| 层 | 内容 | 约束来源 |
|---|---|---|
| 系统信封 | object_id、owner、version、created_at、lifecycle、policy_version | 服务端生成或校验；模型不能指定他人owner |
| 语义描述 | kind、title、schema_ref可空、tags、relationships | 用户作用域内可扩展；标签不是权限 |
| 业务内容 | payload：任意受大小/深度约束的JSON对象或结构化段落 | 不强迫未知业务字段通过固定枚举 |
| 来源声明 | evidence：来源ID、内容定位、作用路径、归因方式 | 服务端核验来源归属和版本，原句支持性独立校验 |
| 消费能力 | eligibility与missing_evidence | 服务端按消费者计算，不接受模型自称“已验证” |

业务键可使用中文，也可使用稳定机器名配中文label；不要求用户先学会字段命名。未知单位保留原词、标注不可换算。嵌套复杂内容可以拆成有关系的多个对象，不为了适配32KB显示卡限制截断原记录；存储、单次工具请求和显示组件分别有可观测资源预算。

示例为工具提议，不是可直接信任的服务端结果：

```json
{
  "kind": "personal.training_experience",
  "title": "今天的腿部训练",
  "payload": {
    "用户描述": "今天练了腿，很累",
    "完成自述": true,
    "感觉": {"原词": "很累"},
    "训练细节": null
  },
  "evidence": [
    {"source_ref": "message:<uuid>", "path": "/用户描述", "attribution": "user_report"},
    {"source_ref": "message:<uuid>", "path": "/完成自述", "attribution": "user_report"},
    {"source_ref": "message:<uuid>", "path": "/感觉", "attribution": "user_report"}
  ],
  "presentation": {"component": "summary", "suggested_label": "训练记录"}
}
```

用户的完成自述可以直接保留。智能体不能据“很累”填入RPE9、某块肌肉fatigue90或未经陈述的组数；这些若仅为推测必须单独标model_hypothesis，且不能进事实计算。

## 5. 来源、认知状态和完成状态分离（AU-04）

单一confidence百分比不能替代证据。每个声明独立记录user_report（用户陈述）、user_confirmed（明确确认提议）、derived（有输入版本和规则的计算）、model_hypothesis（待验证推测）、external_reference（已审核来源）。明确用户陈述不必再次确认才能记为user_report，但也不宣称外部验证过。

对象lifecycle为active/archived/deleted；用户训练活动activity_status可为reported/ongoing/finished/unknown，只有用户证据才能标finished；projection_status为none/partial/ready/failed，可随补充发生变化。三组状态独立：finished+partial是一条已经结束但细节不足的正式记录，不是“保存失败”或必须永久挂起的草稿。

假设过期、用户纠正、来源撤回时使相关声明失效；不影响无关字段。用户说“记不清重量”记录knowledge_state=unknown；“不想提供”记declined并尊重不追问；不能用null和0互换。不同语境冲突先保留双方时间与适用范围，例如工作日/周末可用时间不同，不自动判一方错误。

## 6. 先记录后规范化，按消费者判断（AU-05）

| 消费者 | 最低证据 | 信息不足时 |
|---|---|---|
| 个人时间线 | 已授权的个人陈述与来源 | 仍可保存，时刻不详就显示未知/范围 |
| 对话个性理解 | 本轮相关已授权陈述 | 局部使用，假设与事实分开 |
| 训练组投影 | 动作/条目关联、组身份及已知计量 | 能映射多少映射多少，未知重量允许null并说明 |
| A0肌肉指数 | 已报告完成、适用映射、已知工作组/次数及有效时间依据 | 不满足的部分不计算，返回覆盖与原因 |
| e1RM/吨位 | 同动作和负重口径、具体重量/次数 | 不显示数值，不阻断时间线 |
| 计划履约 | 已有occurrence/目标对应关系与完成证据 | 显示reported_unverified或not_evaluable，不强行100% |
| 自动调整负荷 | 已审核规则要求的相关限制和可比事实 | 提供不依赖该负荷的方案，或只问关键问题 |
| 主动提醒投递 | 有效授权/调度窗口/业务相关性 | 可以提出关注事项但不擅自发送 |

eligibility结构包含consumer_id、state=eligible/partial/ineligible、reason_codes、evidence_refs、evaluated_revision、policy_version。用户界面不暴露内部错误字段名，只解释“已记下；暂不能计算训练量”。`missing_evidence`是某个消费者的缺口，绝不是必须弹给用户的待填问卷。

A0原公式不因自由记录而扩张有效性；例如已知动作和4组×10次、重量未知时，A0不依赖重量，可以计算已知部分，力量/吨位不可计算。只有“练了腿”时不生成4组、动作ID或具体疲劳值。覆盖区间与适用对象缺失须标记，不能只给漂亮的确定数。

## 7. 渐进画像与任务就绪（AU-06）

不设全局“资料完整”门槛。身份和用途授权是前置；业务就绪由当前动作决定。介绍动作不需要用户体重；安排今天的短时自重活动不需要全年目标；提高个人负重才需要相关训练证据与限制。用户可以直接说“我只有15分钟，想活动一下”，系统先完成可行任务。

目标是自由表达对象，如“能陪孩子爬山”“恢复训练习惯”“不想每天被数字催着走”；增肌/力量等只是可选检索标签，不能强行归类或要求只选一个。关联目标、临时状态和长期偏好有不同有效期，临时疲劳不能永久写成性格。

智能体按信息价值提问：问题是否会实质改变本次行动？是否能采用透明且可撤销的假设？用户是否已拒绝？默认每轮0—2问是体验建议，不是固定收集流程；用户主动要求详细访谈时可以调整。敏感缺口只影响确实依赖它的建议，不封锁全部功能。

## 8. 计划自由度与可执行边界（AU-07）

计划payload可采用单次、数日、按次轮换、事件条件或开放目标等结构，7日只是模板之一。主计划仍可唯一，但内部可有多个模块与可选路径，临时一次训练不必替换整个主计划。系统固定可执行动作的身份、适用性和授权，不固定整份计划的栏目和长度。

先区分“建议叙述/探索草稿”和“可执行承诺”。叙述可包含尚未决定日期、目标组或条件的部分；只有要物化成提醒、目标组比较或具体训练执行时，才让对应适配器验证所需信息。纯休息、学习动作、回访状态等节点可以存在，没有组数就不计算组完成率。没有日期的轮换项不自动到期，不记missed。

用户提出“按上次偏好替我安排明天”可构成明确的一次委托；Agent生成后仍须校验，但不一律加一道重复“确定吗”。如果涉及超出意图的目标改变、无法判断的健康风险或重大负荷变化，再请求针对性的确认。授权含义见AU-09，不能由模型自己给自己授权。

## 9. 自定义类型、语义映射与指标（AU-08）

Agent可创建personal.*类型、嵌套字段、个人关联和显示提示，schema_ref可空；第一次记录新概念不用等待全局注册。可生成描述性JSON Schema作为后续校验帮助，旧对象保留旧schema版本，不因新字段变required而自动失效。

强制必填只用于身份/执行效果/确实需要该字段的消费者；个人类型schema不允许一键把全部payload键标required，也不能给已保存未知值补默认事实。字段重命名用语义别名或显式映射，不静默混淆“单只重量”“总重量”。

映射登记保存source_paths、target_adapter、adapter_version、unit_conversion、evidence和status。Agent可以提议映射，平台只执行已注册的声明式操作（单位换算、筛选、已知聚合、字段路径映射），不执行生成Python/SQL/JS。新的生理/风险算法必须审核后成为适配器；新个人名词不因形似健康指标就获得这种计算资格。

个人自定义指标如“我觉得今天精神如何”可存文本或用户自选等级并画趋势；必须保留量表名称与版本。换量表后不能拼成一条可比曲线。不得把主观等级升级成临床量表结论。公共动作/知识的发布仍受专家和版权审核，用户记下一个不在库中的动作不等于该动作已获推荐资格。

## 10. 执行授权与自主策略（AU-09）

| 类别 | 可自主范围 | 何时升级 |
|---|---|---|
| R0 读取/草拟/组织视图 | 有读取权限即可，来源授权不变 | 需要新数据用途或对外传输 |
| R1 明确自述保存/可逆个人组织 | 用户当前意图覆盖即可，可给回执与撤销 | 修改已确认事实、存在语义冲突 |
| R2 计划/日程/执行目标调整 | 当前明确指令或有效委托覆盖时直接验证执行 | 超出委托、重大负荷改变、关键限制不明 |
| R3 删除事实/导出/注销/外部发布收费 | 沿用独立确认、再认证或专门阶段流程 | 不允许靠宽泛“你看着办”跳过 |

风险类别由能力注册表声明并由服务端结合对象和实际效果复核，不信任Agent提交的risk=low。当前对话指令作为intent_ref可无需新建长期委托；长期自主调整需一个可见可撤销的mandate（委托）：对象范围、允许动作、效果约束、有效期、次数/频率限额和用户同意证据。资源限制保存在服务端，payload字段不能扩大权限。

用户可以说“这周时间变动你帮我调整，别加训练量”，范围明确时直接登记有限委托并给回执，只有实际歧义才核对，而非替用户决定训练强度、诊断、购买、删除等所有事项。负荷不可比/输入不明时“不增加负荷”无法证明，不能当作约束已满足。需提议更保守可验证调整或询问。

委托执行产生变更回执及可逆修订入口；停止委托后撤销后续执行能力，已提交事实保留。每次检查consent_version、mandate_version、expiry及使用次数，在同一事务记录授权使用。一次确认必须绑定变更内容和依赖版本，不能生成确认A却执行B。

## 11. 变化集与工具能力（AU-10）

优先暴露少量可组合能力：discover_capabilities、read_context、record_observation、propose_changes、validate_changes、commit_changes、compose_view、schedule_followup。工具并非固定的业务表单合集；具体能力描述返回输入信封、可用效果、权限、当前必要证据及结果schema。

changeset包含多种操作与依赖，例如“记下今天腿部训练→补充疲劳自述→更新今日卡片→给出明天调整草稿”。能同事务提交的变化组成atomic_group；读检索和模型生成在事务外。跨数据库/外部通知使用outbox，结果分别显示，不承诺全局原子事务。

validate返回可执行/待确认/部分可用/拒绝、rule_id、补救选项；Agent可删去无必要操作、改写方案或提问。拆分调用时commit需要服务器验证凭据并再次检查版本、授权、删除墓碑和必要内容状态；验证令牌绑定操作哈希且短期有效。持有验证令牌不等于获得用户授权。

恢复幂等键跨run绑定稳定operation_id、object_id与source_revision；不因为模型重新组织任务就多写一份。修改旧事实用语义patch到灵活对象，服务端构建完整修订和受影响投影，Agent不必把整张训练表抄回去。明确定义replace/remove/append/link，禁止把不带字段解释的任意SQL传给网关。

## 12. 自由编排与运行预算（AU-11）

Profile/TrainingRecord/Plan等子图是可复用能力模板，不是固定六选一业务路由。主教练按目标建立任务DAG，可以跳过建档、交织检索与记录、先交付有用部分再跨轮补充。未识别意图可以进入general_assist，保持读/记/草拟等最小权限，不能凭路由失败直接拒绝已授权的个人记录。

固定4次模型/6次工具/24节点改为**服务端按任务分配的预算档**：quick、standard、deep。v1.1的标准预算可作为standard初始配置；复杂任务可申请deep，预算控制器依据任务规模、用户配额、期限和费用决定，不要求用户每多一次工具就批准。Agent不能通过无限子任务或新run重置同一task_id累计预算。

每次重复调用需要带来新证据或推进状态；同输入/同结果无进展达到阈值时收束。时间/费用达到上限保存中间产物、明确未完成项。用户显式发起深度任务可异步持续到批准预算结束；后台主动生成仍受独立授权、频控和任务生命周期，不创建无限自唤醒链。

## 13. 展示自由与真实业务（AU-12）

渲染器从“每种业务一张固定表”转为组件树：section、text、key_value、list、table、metric、chart、timeline、exercise_reference、action等。Agent可选择哪些字段显示、顺序和中文标签，可将多个对象组合为一个视图，也可完全用自然语言回复。

未知业务kind走通用树/键值/文本组件；未知组件安全回退，不丢原对象。客户端提供支持的component/version清单，服务端验证树深、节点数、数据绑定和动作能力；模板中的HTML/脚本/远程可执行代码不运行。组件白名单约束执行能力，不限制用户的业务词汇。

前端操作可提交自由文本片段或语义patch，服务端执行与聊天同一changeset流程；不要求填满隐藏字段。稳定返回/退出/隐私入口和用户置顶/隐藏选择不由Agent移动。图表数据只能来自带来源的已存值或可追踪计算，禁止生成好看的虚构趋势。

## 14. 数据生命周期与长期演进（AU-13）

个人语义对象、原句摘录、claims、schema、映射、投影、视图、记忆及任务检查点都纳入相同用户归属与删除图。灵活payload不能藏匿未经授权健康数据；用途分类由平台规则/检测加保守回退决定，Agent建议不能降级敏感性。

保存用户记录可复制必要原句摘录并记录用途和期限；对话到期清除不自动让授权保留的训练记录失去全部证据，导出需解释两者不同期限。用户主动删除对应记录则同时删除摘录和派生副本；不可借“不可变审计”无限保留正文。原消息删掉而用户保留独立训练记录时明确展示选择和范围，不能偷偷永久复制聊天。

schema或模型升级先影子映射/比较，不自动改写历史用户自述。公开内容版本回滚和个人schema回滚分别进行。实现仍采用PostgreSQL JSONB、关系索引、LangGraph和已有存储，不引入新平台依赖；在未建业务数据库的阶段按v1.3的M0子集冻结首次迁移，后置实体随功能演进。

## 15. 不变量与自由度验收（AU-14）

必须同时证明两件事：未登记的新业务信息确实能被理解/保存/展示；已授权边界、来源和确定性计算没有失守。不能只用“任意JSON能入库”证明灵活，也不能只看安全拒绝率证明成功。

关键结果：未知属性无需新增数据库列即可回读；缺组次记录可保存且不补造；无完整画像能完成不依赖画像的任务；用户改口后旧投影失效；相同活动从原句补齐到精确记录只计一次；授权范围内调整不重复确认；越界动作准确拦截；新任务表达可通过通用能力组合完成。

完整场景见26，案例及量化评测见27。业务实现尚未开始，本文不是已经具备自主执行能力的声明。

## 16. 权限更开放，首版实现更集中

明确任务或持续委托授予的是完成一组相关工作的权限，不是单个按钮权限。Agent可在该范围内自由读写、主动调整、检索迭代及组织视图；当前用户纠正可直接修改历史源事实，不因R1表中的“修改已确认事实”一律要求再确认。只有真实歧义、超范围或高影响才升级。

M0通过apply_changes合并提议/验证/提交为一次工具调用，内部一致性步骤保持；Agent不必逐次申请读、记、改、显示权限。简单可靠的对象与通用组件已足以保留开放表达，不先建设通用低代码平台。持续自主调整在前台触发，离线执行后置；接口缺失如实说明，不能以宽泛权限冒充已实现能力。

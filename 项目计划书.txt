# 第一章 项目概述

## 1.1 项目名称

**FitMind** —— 一个以对话为核心、由智能体自主驱动、拥有专业健身知识库的健身房私人教练小程序。

## 1.2 项目背景

### 1.2.1 传统健身App的困境

| 问题 | 具体表现 |
|:---|:---|
| 工具化严重 | 用户需要自己填表、选计划、记数据 |
| 缺乏主动性 | App被动等待用户操作 |
| 计划僵化 | 固定模板，无法动态调整 |
| 数据孤岛 | 训练、身体、计划各自独立 |
| 缺乏陪伴 | 没有真实教练的沟通感 |
| 千篇一律 | 所有用户看到相同界面 |
| 知识浅薄 | 只有动作名称，没有专业指导 |

### 1.2.2 真实私教的价值

- **主动沟通**：会问"昨天练完腿，今天感觉怎么样？"
- **动态调整**：根据当天状态调整强度
- **长期陪伴**：记住历史、偏好、伤病
- **个性化**：为每个用户定制方案
- **专业指导**：知道动作怎么做、器械怎么用
- **情感连接**：鼓励、督促、理解

### 1.2.3 项目机会

大语言模型、AI Agent、RAG技术的成熟，使得用AI复现"私教关系"成为可能。

## 1.3 项目定位

**一个像真实私教一样的健身智能体小程序。**

| 特征 | 说明 |
|:---|:---|
| 对话为核心 | 用户与系统之间最重要的交互是对话 |
| 智能体主动 | 主动的教练，不是问答机器人 |
| 数据自由 | 智能体为每个用户自定义字段和结构 |
| 展示自由 | 展示内容由智能体自主生成 |
| 持续演进 | 对用户的认知持续累积 |
| 独立轨迹 | 为每个用户创建独立训练轨迹库 |
| 专业知识 | 拥有可溯源的健身知识库 |
| 肌肉追踪 | 细化到每一块肌肉的状态可视化 |

## 1.4 核心差异

| 维度 | 传统健身App | FitMind |
|:---|:---|:---|
| 交互方式 | 用户填表 | 智能体对话引导 |
| 数据结构 | 固定字段 | 智能体自定义卡片 |
| 计划生成 | 固定模板 | 智能体自主编排 |
| 数据记录 | 用户主动记录 | 智能体主动提问 |
| 界面展示 | 固定面板 | 智能体动态组装 |
| 产品属性 | 工具 | 教练 |
| 知识来源 | 无或浅薄 | RAG专业知识库 |
| 肌肉追踪 | 整体部位 | 逐块肌肉 |
| 可视化 | 简单进度条 | 人体热力图 |

## 1.5 目标用户

| 用户类型 | 特征 | 核心需求 |
|:---|:---|:---|
| 健身新手 | 刚接触，不懂动作和计划 | 引导、教育、鼓励 |
| 进阶训练者 | 有经验，遇到瓶颈 | 突破、调整、监督 |
| 忙碌上班族 | 时间有限，训练不规律 | 灵活、高效、提醒 |
| 康复训练者 | 有伤病，需要谨慎 | 安全、专业、关注 |
| 健身房会员 | 有场地器材，缺乏指导 | 计划、记录、反馈 |

## 1.6 项目愿景

**让每个人都能拥有一个真正懂自己、有专业知识、能看到自己每一块肌肉进步的AI私教。**


# 第二章 核心理念与设计原则

## 2.1 设计哲学

**系统提供骨架，智能体决定血肉。**

| 层级 | 谁决定 | 说明 |
|:---|:---|:---|
| 交互方式 | 我们固定 | 对话为主，允许主动提问 |
| 回答格式 | 我们固定 | 必须包含thinking、reply、actions |
| 工具接口 | 我们固定 | 智能体可调用的工具列表 |
| 安全边界 | 我们固定 | 不能做什么 |
| 数据结构 | 智能体自由定义 | 卡片内容、字段、类型 |
| 展示内容 | 智能体自由生成 | 面板、卡片、文案 |
| 业务逻辑 | 智能体自由编排 | 计划、调整、目标 |
| 提问时机 | 智能体自由决定 | 何时主动、问什么 |

## 2.2 核心原则

### 原则一：对话即交互

用户与系统之间最重要的交互行为是**对话**。所有功能都可以通过对话触发或完成。表单、按钮、面板只是对话的补充。

### 原则二：智能体主动

智能体不是问答机器人，而是**主动的教练**。

- 主动发起对话
- 主动提问
- 主动建议
- 主动调整
- 主动关心

### 原则三：数据自由

智能体可以为每个用户**自定义字段**。用户A有"粗腿倾向"标签，用户B有"产后恢复"备注，用户C有"久坐腰疼"描述——这些都是智能体在对话中自然生成的。

### 原则四：展示自由

面板展示什么、用什么图表、文案怎么写，全部由智能体决定。

### 原则五：持续演进

智能体对用户的认知是**持续累积**的。每次对话、训练、反馈，都会更新智能体对该用户的理解。

### 原则六：独立轨迹

为每个用户创建**独立的训练轨迹库**，记录训练完成项目、消耗能量、刺激肌肉群、完成时间等。

### 原则七：专业可信

智能体的专业知识来自**可溯源的RAG知识库**，不是大模型自身可能过时或错误的知识。回答时标注来源。

### 原则八：肌肉级追踪

身体状态追踪细化到**每一块肌肉**，用人体热力图直观展示，让用户看到每一块肌肉的进步。

## 2.3 智能体人格设定

| 特征 | 说明 |
|:---|:---|
| 专业 | 了解运动科学、训练原理、营养基础 |
| 耐心 | 不急于推进，允许用户慢慢来 |
| 观察力强 | 从只言片语中捕捉关键信息 |
| 主动但不冒犯 | 会提问，但不让用户感到被审问 |
| 诚实 | 不知道就说不知道，不编造 |
| 鼓励但不虚假 | 真诚肯定进步，不夸张 |

## 2.4 设计约束

### 我们固定的东西

| 固定项 | 说明 |
|:---|:---|
| 对话接口 | 用户输入 → 智能体输出 |
| 回答格式 | 必须包含thinking、reply、actions |
| 工具调用规范 | 智能体可调用的工具列表 |
| 记忆存储方式 | 如何持久化智能体的决策 |
| 安全边界 | 不能做什么 |
| 卡片基础结构 | card_id、user_id、title、type、content、display |

### 智能体自由的东西

| 自由项 | 说明 |
|:---|:---|
| 数据结构 | 卡片内容、字段、类型 |
| 展示内容 | 面板、卡片、文案 |
| 业务逻辑 | 计划、调整、目标 |
| 提问时机 | 何时主动、问什么 |
| 卡片组织 | 创建多少、放哪里、怎么展示 |
| 对话风格 | 根据用户调整语气 |

## 3.3 数据流

### 3.3.1 用户发起对话

```
用户输入 → 服务端 → 智能体核心 → 对话引擎解析意图
→ 记忆系统检索相关记忆 → RAG检索相关知识（如需要）
→ 推理引擎决策 → 工具系统调用工具 → 数据层更新
→ 返回结果 → 用户端展示
```

### 3.3.2 智能体主动发起

```
主动调度器检查触发条件 → 发现触发条件 → 生成主动消息
→ 服务端推送 → 用户端展示 → 用户响应 → 进入正常对话流程
```

### 3.3.3 用户操作卡片

```
用户点击卡片/按钮 → 前端发送事件 → 服务端接收
→ 事件系统处理 → 通知智能体 → 智能体推理
→ 更新卡片/执行动作 → 推送前端 → 用户看到变化
```

# 第四章 智能体核心设计

## 4.1 对话引擎

### 4.1.1 职责

管理智能体与用户的对话流程。

### 4.1.2 核心机制

| 机制 | 说明 |
|:---|:---|
| 多轮对话管理 | 记住上下文，理解指代 |
| 意图识别 | 判断用户想做什么 |
| 对话状态追踪 | 知道当前处于哪个阶段 |
| 主动发起 | 在合适时机主动开启新话题 |
| 情绪感知 | 识别用户情绪，调整回应方式 |

### 4.1.3 对话状态机

```
空闲 → 意图识别 → 建档/训练/查询/闲聊 → 完成 → 空闲
```

### 4.1.4 对话流程示例

**建档对话**：

```
智能体：你好，我是你的私人教练。先聊聊你的情况吧，你之前有健身经验吗？
用户：练过一段时间，但断断续续的。
智能体：明白，那大概练了多久？主要练什么？
用户：半年吧，就是随便练练，没有系统计划。
智能体：好的。那你现在最想改善的是什么？比如增肌、减脂、还是塑形？
用户：想增肌，但不想练太壮。
智能体：了解，想要精壮型。那我再问几个问题，帮你制定一个适合的计划。
```

**训练对话**：

```
用户：我今天练完了
智能体：好的，练了什么？
用户：卧推，4组，每组10次，60公斤
智能体：收到。感觉怎么样？轻松、适中、还是吃力？
用户：适中
智能体：好的，我记录一下。要不要继续练飞鸟？
```

**主动对话**：

```
智能体：嘿，你上次练腿是3天前了，今天要不要安排一下？
用户：今天有点累
智能体：那要不今天休息，明天再练？或者只做轻度的拉伸？
用户：行，明天吧
智能体：好的，我帮你把腿部训练排到明天。
```

### 4.1.5 意图识别

| 意图 | 示例 | 处理 |
|:---|:---|:---|
| 记录训练 | "我今天练了卧推" | 提取动作、组数、重量 |
| 修改目标 | "我想改成减脂" | 更新目标卡片 |
| 查询状态 | "我最近练得怎么样" | 检索训练历史，生成总结 |
| 请求建议 | "我明天该练什么" | 根据计划回答 |
| 问知识 | "上斜哑铃卧推怎么做" | 检索RAG知识库 |

# 第五章 资料卡系统

## 5.1 设计理念

**资料卡是智能体管理信息的原子单元。**

传统系统用固定的"表"和"字段"组织数据，本系统让智能体以**资料卡**为基本单位，自由地为每个用户创建、组织、展示信息。

## 5.2 资料卡的本质

一张资料卡 = **信息容器 + 展示规则 + 位置绑定**

```json
{
  "card_id": "string",
  "user_id": "string",
  "title": "身体状态",
  "type": "data | task | list | custom",
  "content": {},
  "display": {
    "location": "sidebar | main | dialog | floating",
    "style": "card | list | chart | text",
    "priority": 1,
    "visible": true
  },
  "created_at": "timestamp",
  "updated_at": "timestamp"
}
```

## 5.3 资料卡示例

| 卡片 | 标题 | 类型 | 位置 | 内容示例 |
|:---|:---|:---|:---|:---|
| 卡1 | 身体状态 | data | 侧边栏 | 身高175，体重70，体脂18% |
| 卡2 | 今日训练 | task | 主界面 | 已完成：卧推4组；未完成：飞鸟3组 |
| 卡3 | 可用器材 | list | 侧边栏 | 哑铃、杠铃、龙门架、跑步机 |
| 卡4 | 肌肉状态 | muscle_heatmap | 主界面 | 逐块肌肉状态 |
| 卡5 | 近期目标 | text | 侧边栏 | 3个月内卧推达到80kg |
| 卡6 | 训练偏好 | list | 侧边栏 | 喜欢自由重量，讨厌跑步机 |

| 卡8 | 本周计划 | task | 主界面 | 周一胸、周二背、周四腿... |

**注意**：以上只是示例。实际运行时，智能体会根据每个用户的具体情况，自行决定创建哪些卡片、卡片里放什么、放在哪里。

## 5.4 卡片的能力

### 智能体可执行的操作

| 操作 | 说明 |
|:---|:---|
| create_card | 创建新卡片 |
| update_card | 更新卡片内容 |
| delete_card | 删除卡片 |
| merge_cards | 合并两张卡片 |
| move_card | 改变卡片位置 |
| show_card | 在对话中展示某张卡片 |
| hide_card | 隐藏卡片 |
| reorder_cards | 调整卡片顺序 |

## 5.5 卡片与对话的关系

资料卡不是独立的界面元素，而是**对话的延伸**：

- 对话中触发：智能体在回复中嵌入卡片
- 对话外展示：卡片放在主界面/侧边栏，用户可随时查看
- 点击卡片：用户点击卡片可展开、编辑、或与智能体讨论
- 智能体主动更新：智能体在后台更新卡片，用户下次打开看到最新内容

## 5.6 卡片的生命周期

```
创建 → 活跃 → 更新 → (合并/拆分) → 归档 → 删除
```

## 5.7 卡片与界面的关系

**界面 = 智能体为当前用户动态组装的卡片集合**

- 用户A是新手：智能体给他展示"基础动作学习卡"
- 用户B是老手：智能体给他展示"周期化训练卡"
- 用户C有伤病：智能体把"康复训练卡"放在最显眼位置

## 5.8 卡片系统的优势

| 优势 | 说明 |
|:---|:---|
| 极致灵活 | 为每个用户定制完全不同的信息结构 |
| 对话延伸 | 卡片是对话的自然延伸 |
| 动态演进 | 随着对用户了解的深入，卡片不断增加调整 |
| 无需预设 | 不需要预先设计"用户画像表" |
| 可追溯 | 每次变更都有版本记录 |
| 可迁移 | 卡片结构通用，可导出、可迁移 |

### 7.4.6 动态SVG生成

```typescript
export function generateMuscleSvg(
  view: 'front' | 'back',
  states: MuscleState[],
  width: number = 200,
  height: number = 300
): string {
  const viewMuscles = musclePaths.filter(m => m.view === view);
  const stateMap = new Map(states.map(s => [s.muscleId, s]));
  
  const muscleElements = viewMuscles.map(muscle => {
    const state = stateMap.get(muscle.id);
    const fill = state ? COLOR_MAP[state.status] : '#D9D9D9';
    const opacity = state?.selected ? 1.0 : 0.6;
    const stroke = state?.selected ? '#4A90D9' : 'none';
    
    return `<path d="${muscle.path}" fill="${fill}" 
      fill-opacity="${opacity}" stroke="${stroke}" 
      data-muscle-id="${muscle.id}"/>`;
  }).join('');
  
  return `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 200 300" 
    width="${width}" height="${height}">
    <path d="${getBodyOutline(view)}" fill="#F0F0F0" 
      fill-opacity="0.3" stroke="#E8E8E8"/>
    ${muscleElements}
  </svg>`;
}
```

## 8.5 RAG检索流程

### 8.5.1 整体流程

```
用户提问 → 智能体理解意图 → 生成检索查询
→ 向量检索 + 关键词检索 → 重排序
→ 返回Top-K知识 → 智能体结合知识生成回答 → 标注来源
```

### 8.5.2 检索策略

| 策略 | 说明 |
|:---|:---|
| 向量检索 | 语义相似度，适合模糊查询 |
| 关键词检索 | 精确匹配，适合专业术语 |
| 混合检索 | 两者结合，效果最好 |
| 分类过滤 | 按category过滤 |
| 标签过滤 | 按tags过滤 |
| 重排序 | 用交叉编码器重排 |

### 8.5.3 检索实现

```python
class KnowledgeRetriever:
    async def retrieve(self, query, top_k=5, category=None, tags=None):
        query_embedding = await self.embedder.embed(query)
        
        vector_results = await self.db.search_by_vector(
            query_embedding, top_k=top_k * 2, category=category, tags=tags
        )
        
        keyword_results = await self.db.search_by_keyword(
            query, top_k=top_k * 2, category=category, tags=tags
        )
        
        merged = self.merge_results(vector_results, keyword_results)
        reranked = await self.reranker.rerank(query, merged)
        
        return reranked[:top_k]
```

**计划生成逻辑**：

```
输入：用户档案 + 目标 + 轨迹库 + 肌肉状态
输出：训练计划

步骤：
1. 根据目标确定训练方向
2. 根据训练年限确定强度
3. 根据一周几练确定分化方式
4. 根据偏好选择动作
5. 根据肌肉状态避免重复刺激未恢复肌肉
6. 生成周期化计划
```

# 第十二章 智能体行为规范

## 12.1 回答格式

```json
{
  "thinking": "思考过程（内部使用）",
  "reply": "给用户的回复",
  "actions": []
}
```

## 12.2 行为准则

### 应该做的

- 主动了解用户情况
- 根据用户状态调整建议
- 记住用户说过的话
- 在合适时机主动提问
- 诚实，不知道就说不知道
- 鼓励用户，但不虚假夸赞
- 专业问题检索知识库，标注来源

### 不应该做的

- 不提供医疗建议
- 不强迫用户
- 不编造数据
- 不忽视用户反馈
- 不千篇一律
- 不编造知识来源

## 12.3 安全边界

- 不提供医疗诊断
- 不推荐药物
- 不鼓励过度训练
- 不忽视伤病信号
- 遇到危险信号建议就医

## 12.4 提问规范

- 提问要自然，像聊天
- 不要连续问太多问题
- 给用户选择
- 根据上下文提问，不重复

# 第十四章 关键挑战与应对

| 挑战 | 应对 |
|:---|:---|
| 智能体乱存数据 | schema校验 + 版本控制 |
| 智能体忘记用户 | 强化记忆系统，定期总结 |
| 智能体回答不稳定 | 固定格式 + 温度调节 + 示例引导 |
| 智能体编造知识 | 强制检索RAG，标注来源 |
| 数据迁移困难 | 通用存储层，支持导出 |
| 用户不愿对话 | 降低门槛，主动引导 |
| 智能体成本高 | 缓存 + 小模型 + 按需调用 |
| 隐私问题 | 加密 + 脱敏 + 权限控制 |
| 卡片过多 | 软上限 + 自动归档 |
| 卡片结构混乱 | 类型参考 + 定期整理 |
| 卡片渲染复杂 | 通用渲染器 + 组件化 |
| 事件处理延迟 | 异步处理 + 队列 |
| 肌肉状态计算复杂 | 缓存 + 增量计算 |
| SVG性能 | 缓存 + 局部更新 |
| 知识库质量 | 审核 + 用户反馈 + 定期审查 |
